# Starbucks Study Spot Planner — Build Plan

## Goal

Decide **which of ~10 Starbucks stores in Singapore to go to, at what time**, to maximise the chance of getting a usable study seat.

Two data sources:

1. **Google Popular Times histogram** — the weekly busyness curve per store. A rolling multi-month average, so it changes slowly. This is the prior.
2. **My own seat log** — what actually happened when I showed up. This is the correction, and it's the part Google can't give me.

## Non-goals (explicit — do not build these)

- No live / real-time busyness. No "check now" button.
- No backend, no server, no API keys in the deployed app.
- No auth, no multi-user, no accounts.
- No native iOS app.

Any of these can be revisited later. None are in scope.

## Architecture

Everything is either a **local Python script** (run manually on the Mac) or a **static page** (deployed, read-only).

```
starbucks-planner/
├── scraper/
│   └── fetch_histograms.py     # run monthly on Mac
├── analysis/
│   └── calibrate.py            # run occasionally on Mac
├── data/
│   ├── stores.json             # generated by scraper, committed
│   └── calibration.json        # generated by analysis, committed
├── web/
│   ├── index.html              # static SPA, no build step preferred
│   ├── app.js
│   └── style.css
└── Makefile                    # `make refresh` = scrape + calibrate
```

**Deploy target:** GitHub Pages or Cloudflare Pages. Static files only. The app fetches `data/*.json` as relative paths.

**Seat logging:** Apple Shortcut on iPhone appends a row to a CSV in iCloud Drive. The Mac reads the same file via the local iCloud path. No sync code to write — iCloud does it.

### Why this shape

The histogram is near-static, so there is no reason to fetch it at request time. Generating JSON on the Mac and committing it means the deployed app has zero runtime dependencies and cannot break because Google changed its HTML. When the scraper breaks, it breaks on my laptop where I can see it, not in front of me at 9am on a Saturday.

## Frontend: plain HTML, no framework

**Decision: vanilla HTML/CSS/JS. No React, no Vite, no build step.** A single `index.html`, one stylesheet, a couple of JS modules. Deployable by pushing the files.

Rationale: at Phase 1 scope, React and vanilla cost about the same to write — one view with two pieces of state is the same amount of code either way. React's advantage only shows up at Phase 3, and it's worth maybe two hours across the whole build. Against that, a dependency tree costs a few hours a year in upkeep and will greet me with build errors the first time I touch it after a long gap. For a tool I open twice a week and want working in March without maintenance, that trade is bad.

Add a **web app manifest** so this can be added to the iPhone home screen with a proper icon and no Safari chrome. That's ~20 lines and gets most of what "feels like an app" means here. No service worker in v1 — offline caching is a real want if any store is in a basement mall, but stale-cache bugs are miserable to debug and this shouldn't carry that cost until the problem actually appears.

Not native iOS. Nothing here needs App Store review or a developer account.

### Constraints — write vanilla in a React-shaped way

These are non-negotiable. They cost nothing now and make a later React port mechanical rather than a rewrite.

1. **One state object. Never read state back out of the DOM.** To know which day is selected, read `state.selectedDay`, not a class on a button. Implicit state living in the DOM is the single thing that makes a vanilla→React port painful.
2. **One `render(state)` function.** Every interaction mutates state then calls `render`. Rebuilding the whole grid is inefficient by framework standards and completely irrelevant at ~180 cells. It is also exactly React's mental model.
3. **Pure data functions in their own module**, importing nothing DOM-related — busyness→colour, joining log entries to histogram cells, computing the calibration overlay. These are the majority of the real logic and they must port over untouched.
4. **CSS in a stylesheet with plain class names.** No styles assembled in JS strings.

Use **CSS Grid** for the heatmap. No charting library.

### If React ever happens

Only port if there is a concrete reason — a second view, per-store drill-downs, or wanting this as a portfolio piece. Not because it feels more proper. Most side projects never get the rewrite and that is usually correct.

When it does happen, `stores.json`, the scraper, the CSS, and the pure functions all carry over unchanged. Only the DOM code is discarded — roughly 150–250 lines. `state` becomes `useState`, the explicit `render()` call becomes React calling it, the load `fetch` becomes `useEffect`. An afternoon, if constraints 1–4 were followed.

## Data contracts

### `data/stores.json`

```json
{
  "generated_at": "2026-08-28T10:00:00+08:00",
  "timezone": "Asia/Singapore",
  "stores": [
    {
      "id": "beauty-world",
      "name": "Starbucks Beauty World Centre",
      "place_id": "ChIJ...",
      "lat": 1.3412,
      "lng": 103.7757,
      "histogram": {
        "mon": [{"hour": 7, "busyness": 19}, {"hour": 8, "busyness": 34}],
        "tue": [],
        "wed": [], "thu": [], "fri": [], "sat": [], "sun": []
      },
      "typical_stay_minutes": [30, 90],
      "seats_est": null,
      "notes": ""
    }
  ]
}
```

- `busyness` is 0–100, normalised to **that store's own peak**. Not comparable across stores without calibration. This is the single most important thing to get right in the UI copy.
- Hours absent from the array mean closed.
- `seats_est` and `notes` are hand-maintained by me, not scraped. Leave nulls if unknown.

### `seatlog.csv` (iCloud Drive)

```csv
timestamp_iso,store_id,outcome,note
2026-08-28T14:32:00+08:00,beauty-world,seat_outlet,
2026-08-29T10:05:00+08:00,holland-v,no_seat,queue out the door
```

- `outcome` — `seat_outlet` | `seat_no_outlet` | `no_seat`
- `note` optional, usually empty
- Append-only. Never rewrite this file from code.

Entry must be **two taps**: pick store from a list of 10, pick outcome from a list of 3. Timestamp is automatic. If it takes more than two taps I will stop logging within a week and the whole calibration idea dies.

### `data/calibration.json`

Written by `analysis/calibrate.py`. Shape TBD until Phase 3 — see below.

## Phases

### Phase 0 — Verify assumptions before building

Do not skip this. Three things need checking against reality first:

1. **Resolve the 10 stores to Google place IDs.** Store list is at the bottom of this file — fill in before starting.
2. **Confirm the histogram timezone.** Pull one store, compare the returned curve against what the Google Maps app shows on my phone at a known time. If the hours are offset, find the offset and handle it explicitly rather than assuming SGT.
3. **Confirm the scrape source works.** See "Scrape source" below.

Acceptance: one store's histogram printed to console, visually matching the Maps app.

### Phase 1 — Scraper + heatmap view

`fetch_histograms.py` pulls all 10 stores, writes `stores.json`.

Web app renders a **heatmap**: rows = store, columns = hour of day, one grid per day of week (or a day selector). Colour = busyness.

Requirements:
- Must be readable on an iPhone 15 Pro Max in portrait. Ten rows × ~18 columns is tight; consider a day-at-a-time view with a day switcher rather than seven grids.
- Show `generated_at` prominently so I know how stale the data is.
- A "now" indicator on the current day/hour.

Acceptance: I can open it on my phone and answer "where should I go at 3pm on a Tuesday" without thinking hard.

**Phase 1 is independently useful.** If phases 2 and 3 never happen, this was still worth building.

### Phase 2 — Seat logging

- Apple Shortcut: two-tap entry, appends to `seatlog.csv` in iCloud Drive.
- Web app reads a committed copy of the log and shows my past visits overlaid on the heatmap (a dot per visit, coloured by outcome).
- `make refresh` copies the iCloud CSV into the repo and commits.

Acceptance: logging a visit takes under five seconds standing at the counter.

### Phase 3 — Calibration

Join each log entry to the busyness value for its store/day/hour. Then estimate P(seat) as a function of busyness, per store.

**Do not fit a model until there are enough observations.** Below roughly 30 entries, show the raw log and nothing else. When there is enough data, start with the simplest thing that works — empirical rates by busyness bucket, or a pooled logistic regression with per-store intercepts. A separate model per store will overfit badly at this sample size; pool first.

Whatever the model, the UI must show **uncertainty**, not a bare probability. Ten visits is not a probability.

## Known problems to design around

**Busyness is not seat availability.** Google counts everyone in the geofence, including the takeaway queue. A high-throughput store can read 70% and still have empty tables. This is the entire reason the seat log exists — say so in the UI so I remember why I'm logging.

**Selection bias in the log.** I will only log when I actually go, and I will go at times I already believe are good. So the log will cluster in low-busyness cells and say almost nothing about high-busyness ones — exactly the cells I most need to predict. Two mitigations worth building in:
- Let me log a `no_seat` outcome for a store I walked past or gave up on, not just ones I sat down in.
- Surface which store/time cells have zero observations, so I know where the model is guessing.

**Normalisation across stores.** A 60% reading at a 90-seat store and a 20-seat store mean completely different things. Until `seats_est` is filled in by hand, the heatmap should not imply cross-store comparability. Consider sorting/colouring within-store rather than across.

**Scraper fragility.** Google changes its markup. The fetch layer must be behind a single interface (`fetch_store(place_id) -> Histogram`) so the source can be swapped without touching anything else. Fail loudly and leave the previous `stores.json` intact rather than writing a partial file.

## Scrape source

Options, in order of preference:

1. **SerpApi Google Maps endpoint** — returns `popular_times` as structured JSON. Free tier exists; sources disagree on whether it's 100 or 250 searches/month as of mid-2026, so **check the live pricing page**. At 10 stores refreshed monthly this is ~10 calls/month, comfortably inside either.
2. **`LivePopularTimes` / `populartimes` Python libraries** — free, but scrape Google Maps HTML directly and break periodically.
3. **Apify Google Maps Popular Times actor** — managed, has a free tier.

Note: Google's Places API does **not** expose popular times or busyness. Do not waste time looking for the field.

Terms-of-service note: automated scraping of Google Maps is against Google's ToS. This is a personal tool at ~10 requests a month, but it should not be made public or commercial in this form.

## Build notes

**Model:** run Claude Code on `opusplan` — Opus during plan mode for architecture and reasoning, Sonnet for execution. The hard thinking is already in this file, so most of what remains is mechanical and Sonnet-appropriate. Two places to reach for Opus explicitly: Phase 0 debugging, where a timezone or parse bug will look plausible while being wrong, and the Phase 3 pooling decision, which is a statistical judgement call on thin data. Note that `opusplan` only engages Opus when plan mode is actually active — entering plan mode at the start of each phase is the point.

**Before writing code:** critique this plan against the actual repo and environment. It was written without seeing either.

**Watch for the tipping point.** If Phase 3 turns out to need more interactive state than expected — filtering, comparison mode, per-store drill-downs — hand-rolled state will start to fight back. That is the signal to port to React, not to push through. Constraints 1–4 exist so that door stays cheap to open.

## Open questions

- Does the histogram come back in SGT or UTC? (Phase 0)
- Do all 10 stores actually have popular times data? Smaller or newer outlets may not. If a store has none, the app needs a graceful empty state rather than a blank row.
- Is a heatmap the right primary view, or would a ranked "best store right now / at time X" list be more useful day to day? Build the heatmap first, then decide.
