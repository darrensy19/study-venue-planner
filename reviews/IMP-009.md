### Findings

#### `IMP-009-R1-F01` — Medium — accepts malformed per-venue protocol values as successful validation

- **Status at issuance**: `open`
- **Evidence**: `build/return_validator_bridge.py:65-72` verifies only that stdout is a JSON object and has every expected key. A real Node stub emitting `{\"v1\": null}`, `{\"v1\": {}}`, or `{\"v1\": {\"state\": \"what\"}}` returns normally from `validate_return_transport()` rather than raising `BridgeError`; the tests at `tests/python/test_return_validator_bridge.py:98-112` cover array output and an omitted key, but none of these malformed per-venue values.
- **Impact**: A corrupt, incompatible, or otherwise broken bridge can be accepted as a successful validation result rather than being distinguishable from per-venue `invalid`. A later merge can stamp a non-status value, so it fails the bridge contract that every generated venue receive an `ok` or `invalid` status and fails to give the caller the required stop-before-atomic-replace signal.
- **Recommended correction**: Validate every returned value as the exported function's status schema: exactly `{state: \"ok\"}` or `{state: \"invalid\", reason: <string>}` (and reject any other type/state/shape with `BridgeError`). Add fixture stubs for at least `null` and an unknown state, asserting they are broken-bridge failures; retain the existing real malformed-band case proving a legitimate `invalid` remains an ordinary result.
