### Findings

#### IMP-011-R1-F01 — High — Out-of-order raw entries are accepted and committed

- **Status at issuance**: `open`
- **Evidence**: `PLAN.md:2066` requires raw rows to be append-only and chronological. `build/coarsen.py:136-174` parses each offset-aware timestamp and immediately appends it to `rows`, but keeps no prior timestamp and contains no ordering check. The new test file has malformed-schema cases at `tests/python/test_coarsen.py:159-195`, but no out-of-order raw-row case. Independent probe with a two-row raw file ordered `2026-08-24T10:00:00+08:00` then `2026-08-24T09:00:00+08:00` returned `2` and wrote those reversed `mon/10`, then `mon/9` committed rows.
- **Impact**: A malformed/non-append-only private log is silently accepted, and its reversed relative ordering becomes public committed history. That violates the explicit schema contract and breaks the ordering premise used for “last visit” and later Phase 3 joins.
- **Recommended correction**: Fail closed during raw parsing when a row's absolute offset-aware `occurred_at` is earlier than its predecessor (decide and document the equality rule consistently with append-only input), before any write. Add a fixture that asserts the failure and unchanged raw/committed files; make its ordering check non-vacuous.

### Finding dispositions

#### `IMP-011-R1-F01` — `accepted`

- **Factual assessment**: `confirmed` — independently reproduced the finding before applying any
  fix, with a disposable synthetic fixture matching the reviewer's own repro shape (a two-row raw
  file with reversed `occurred_at` values, no committed file): `coarsen()` returned `2` and wrote
  both rows in reversed order, with no ordering check anywhere in `parse_raw_rows`. `PLAN.md`,
  "The private raw schema" (line 2066) does state "Rows are append-only and chronological," which
  the implementation never enforced.
- **Independent verification**: reran the finding's own reproduction against the pre-correction
  code and confirmed the reversed rows were accepted and committed exactly as reported.
- **Response**: the finding is correct as reported, with one refinement discovered while
  implementing the fix. A first version of the correction checked chronology across the **whole**
  raw file (prefix and suffix alike) and broke three existing, PLAN.md-sanctioned tests:
  `test_coordinated_reorder_of_differing_projections_passes_with_rewritten_order` and
  `test_reorder_among_equal_projection_rows_wholly_in_raw_prefix_passes_byte_identical` construct
  raw files whose rows are deliberately out of `occurred_at` order — PLAN.md's own Group 1 taxonomy
  ("The coarsening stage") explicitly requires a raw-side reorder wholly inside the processed prefix,
  or a coordinated reorder mirrored onto the committed side, to **pass** the comparator. Tracing both
  conflicting tests showed their reordered rows are always fully mirrored by an existing committed
  file (`processed_count == raw_row_count`, i.e. zero suffix rows) — the taxonomy's "reorder passes"
  instances are scoped to the **prefix**, which the comparator checks for projection *consistency*
  with the committed record, not chronology; `data/seatlog.csv` drops `occurred_at` entirely, so
  there is no surviving timestamp to even re-validate a prefix row against. The reviewer's own repro
  (and the fix required) is specifically about the **suffix** — rows this run is coarsening for the
  first time, which is exactly what a fresh, unedited phone append looks like. Rescoped the check to
  `suffix_raw_rows` only (`_validate_suffix_chronological`, called after the suffix is determined and
  before any histogram lookup or write), which resolves the conflict: the reorder tests have no
  suffix at all, so the chronology check never runs for them, while the reviewer's exact scenario
  (no committed file, both rows in the suffix) is still caught. Compares the absolute instant
  (`occurred_at` objects directly), never the derived `Asia/Singapore` local reading, so two rows
  under different UTC offsets that could look ascending by digits alone are still compared correctly
  — added a dedicated regression test for that. Equal-to-predecessor is accepted, not rejected — two
  entries can genuinely share an instant (a rapid double-tap); only a row strictly earlier than its
  predecessor is a reversal — locked in with its own regression test.
- **Changes made**: `build/coarsen.py` — new `_validate_suffix_chronological(suffix_raw_rows)`,
  called once the suffix is known, before deployed-histogram lookup or any write.
  `tests/python/test_coarsen.py` — three new tests: reversed suffix timestamps abort with no output
  change (the finding's own case), the same across differing UTC offsets (proving absolute-instant
  comparison), and equal consecutive timestamps are accepted (locking the equality decision). Both
  new "fail" tests initially shipped with an unrelated `default_venues_json` fixture that only
  populated one of the two hours the two rows resolve to — self-caught during non-vacuity
  verification (mutating the new check to a no-op still raised `CoarsenError`, via the unrelated
  missing-histogram guard, exactly the same masking pattern the pre-gate found in round... invocation
  1 of the gate) — fixed by giving both tests a complete histogram before finalizing this response,
  so the chronology check is genuinely the only thing that can make them fail.
- **Verification**: `.venv/bin/pytest tests/python/ -q` — 131 passed, 0 failed (128 round-1 + 3 new);
  `node --test tests/js/*.test.js` — 178 passed, unaffected; `git diff --check` — passed; every new
  test confirmed non-vacuous by disabling `_validate_suffix_chronological`'s check and observing all
  three fail (two immediately; the third, `test_equal_consecutive_...`, is a positive-path lock and
  was instead confirmed to still pass, since it asserts acceptance, not rejection), then restoring
  the file and re-verifying byte-identical (`sha256`) and all-green.
