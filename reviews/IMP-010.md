### Findings

#### `IMP-010-R1-F01` — High — an invalid-preference venue can still be presented as Plan B

- **Status at issuance**: `open`
- **Evidence**: `rankVenues()` computes `invalidPreference` at `web/ranking.js:1585` and removes those venues only in its primary-candidate loop (`1593-1596`). `selectPlanBFallback()` instead reads fallback venues directly from the complete `venueById` map (`1473-1480`), never checks that map, and copies `fallbackVenue.preference` into its ordering input (`1512-1518`). `compareFallbacks()` deliberately skips the preference key when either side is `undefined` and falls through to `venue_id` (`1459-1463`). Independent reproduction with a valid primary linking to equal, strong fallbacks `bad-a` (missing `preference`) and `good-z` (valid preference) returned both `removed: {venueId:"bad-a", kind:"preference_invalid"}` and `primary.planB: {venueId:"bad-a", strength:"strong"}`. The governed contract says preference validation runs before *any* ordering-key read (`PLAN.md:1575-1580`), an invalid preference is an unranked removal (`1600-1601`), and fallback preference is usable only once it has passed validation (`1620-1644`).
- **Impact**: a venue the same entry point has removed because its ranking order is indeterminate can still be offered to the user as the primary venue's strong Plan B. With two such fallback links, the undocumented `venue_id` fallback silently chooses among invalid records, violating the strict-total-order and fail-closed guarantees.
- **Recommended correction**: thread the already-computed invalid-preference set into fallback selection and skip every fallback venue it contains before evaluation or comparator input. Add entry-point tests for missing/malformed and duplicate preference fallback venues, including a valid competing fallback that proves the invalid one cannot win.
