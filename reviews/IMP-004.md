### Findings

#### IMP-004-R1-F01 — High — Unverified returns use hours-only minutes to qualify as salvage

- **Status at issuance**: `open`
- **Evidence**: `web/ranking.js:493-501` returns `hoursResult.usableMinutesMid` with `metricsBasis: "hours_only"` when the return tier is `unverified`; `web/ranking.js:856-860` passes that value directly to `resolveBackupStrength`; `web/ranking.js:786-789` uses it to clear `PLAN_B_MIN_SESSION_MINUTES`. The end-to-end test explicitly asserts this behavior: `tests/js/ranking.test.js:1640-1643` expects an unverified-return fallback with 180 hours-only minutes to be `salvage`. This conflicts with `PLAN.md` §5 and “Plan B viability floor”, which require the floor minutes and stated salvage duration to be return-capped.
- **Impact**: A fallback with no verified way home can be presented as a salvage option because its venue hours supply 90+ minutes, even though no return-capped session duration exists. This violates the fail-closed floor and gives the later UI no valid “actual duration” to state.
- **Recommended correction**: Keep the required `unverified` cap below `strong`, but do not use hours-only minutes as the return-capped floor/duration. Represent the duration as unavailable for an unverified return and apply the product contract’s unverified-return rule explicitly (or revise the governing contract with user authority if salvage is intentionally allowed without a verified duration). Replace the current end-to-end expectation with a test that proves the chosen fail-closed behavior and that hours-only minutes cannot silently satisfy the return-capped floor.

### Finding dispositions

#### `IMP-004-R1-F01` — `accepted`

- **Factual assessment**: `confirmed` — independent re-reading of `PLAN.md`'s Plan B section (lines
  1423-1437, "backup_strength is amended in two places") confirms `salvage`'s stated duration in the
  unverified-return case must be the **return-capped** `usable_minutes`, never the hours-capped one.
  No such quantity exists when the return tier is `unverified` (no recorded route at all), so feeding
  `resolveOverallFeasibilityAtArrivals`'s hours-only fallback figure into `resolveBackupStrength`'s
  generic `usableMinutesMid >= minSessionMinutes` floor check was wrong whenever the fallback's own
  hours tier was `shorter` — a fallback that does not even fit on hours alone, with an unverified way
  home on top, could still read enough hours-only minutes to clear the 90-minute floor and wrongly
  reach `salvage`.
- **Independent verification**: Re-read `PLAN.md` line 295 (the `robust`/`tight` hours + `unverified`
  return row: "capped at `salvage`, labelled as an unverified way home") and lines 1433-1437 (the same
  rule stated categorically, plus the return-capped-duration requirement). The only case `PLAN.md`
  explicitly grants `salvage` for an unverified return is when the fallback's own hours tier is
  already `robust`/`tight` — a categorical condition, never a minutes comparison. The combination
  (hours tier `shorter`, return `unverified`) is not addressed by name anywhere in `PLAN.md`; failing
  it closed to `none` matches this codebase's dominant discipline for every other case where a claim
  cannot be honestly established (malformed/missing data, `MALFORMED` bands, absent validation stamps,
  etc.), and does not touch or contradict the one case `PLAN.md` does specify.
- **Response**: Accepted as reported. `evaluatePlanBFallback` now resolves the fallback's hours-only
  tier directly (`resolveFeasibilityAtArrivals`) whenever the composed `overall.tier` is `unverified`,
  and applies `PLAN.md`'s categorical rule instead of the generic floor check: `salvage` only when that
  hours-only tier is `robust`/`tight` (reason `unverified_return`, matching the existing, reviewer-
  verified test case unchanged), else `none` (reason `unverified_return_and_short_session`). The
  confidence floor is still checked first in both branches, matching `resolveBackupStrength`'s own
  ordering. `resolveBackupStrength` itself is unchanged — its generic contract (given an actual
  return-capped number, compare it to the floor) still holds and is still exercised by its own unit
  tests; `evaluatePlanBFallback` simply never calls it with an hours-only number dressed up as one.
  The returned object now also carries `metricsBasis` (`"combined"` or `"hours_only"`), so any future
  UI consumer can tell whether `usableMinutesMid` is presentable as a committed duration or must be
  labelled "on hours alone" per `PLAN.md`'s own example phrasing — this closes the finding's "gives
  the later UI no valid actual duration to state" concern without inventing a UI-layer contract this
  assignment doesn't own.
- **Changes made**: `web/ranking.js` — `evaluatePlanBFallback` branches on `overall.tier === "unverified"`
  before delegating to `resolveBackupStrength`, adds the `metricsBasis` field to its return value.
  `tests/js/ranking.test.js` — added
  `"evaluatePlanBFallback: hours-only minutes clearing the floor never grant salvage when the
  fallback's own hours tier is shorter and the return is unverified"` (a fixture with 110 hours-only
  minutes, above the 90-minute floor, whose own hours tier is `shorter`; asserts `strength: "none"`,
  which the pre-correction code would have read as `"salvage"` — confirmed by hand-tracing the old
  code path against this fixture before writing the fix) and added a `metricsBasis` assertion to the
  existing unverified-return test.

  plus the one new regression test; no other test's expected values changed).
