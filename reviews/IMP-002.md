### Findings

#### `IMP-002-R1-F01` — Medium — Default return tolerance is declared but never applied

- **Status at issuance**: `open`
- **Evidence**: `web/ranking.js:23` declares `RETURN_TOLERANCE_MINUTES = 10` and the immediately preceding comment says provisional values are defaulted wherever used. But `resolveReturnFeasibility` destructures `toleranceMinutes` without a default (`web/ranking.js:297-311`), and `resolveOverallFeasibility` forwards an equally optional `returnToleranceMinutes` unchanged (`web/ranking.js:402-432`). First-hand probe with a schedule-bound `23:00-23:05` band, midpoint end 23:07 and upper end 23:10 returned `shorter` when `toleranceMinutes` was omitted, versus `tight` when it was `10`. Every added tier test supplies `toleranceMinutes: 10` (`tests/js/ranking.test.js:775-805`), so the suite does not exercise the advertised default.
- **Impact**: Any ordinary caller that relies on the documented provisional default misranks a return shortfall within ten minutes as `shorter` instead of `tight`. This can lower a venue's overall tier and change recommendation grouping.
- **Recommended correction**: Default `toleranceMinutes` to `RETURN_TOLERANCE_MINUTES` in `resolveReturnFeasibility`, and ensure `resolveOverallFeasibility` preserves that default when `returnToleranceMinutes` is omitted. Add direct and end-to-end tests that omit the return-tolerance parameter and assert the ten-minute boundary remains `tight`.
