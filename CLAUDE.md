# CLAUDE.md

Personal tool for choosing a coffee venue for a 3-6 hour study session — maximising the chance of getting a suitable seat for the whole session, and minimising the wasted trip when that's wrong. Read [plan.md](plan.md) first — it is the spec and the architecture doc; don't duplicate it here. Log decisions and deviations in [decisions.md](decisions.md). Tooling in use: [skills.md](skills.md).

## Workflow

- **Solo project. No cross-agent coordination.** There is no primary/reviewer split, no `HANDOFF.md`, no `reviews/` directory, no role preflight. Other projects on this machine use that pattern; this one deliberately does not. Don't import it.
- Run on `opusplan`. Enter plan mode at the start of each phase — that's what makes Opus engage; without it this session runs on Sonnet.
- Before writing code for a phase, critique plan.md against the repo and environment as they exist right now, not as assumed when the plan was written. Say what's wrong before implementing around it.
- Work one phase at a time, in order (0 → 1 → 2 → 3). Don't build ahead — no Phase 2 seat-logging scaffolding while Phase 1 is open.

## Python environment

`.venv/` plus `requirements.txt`. **Always invoke as `.venv/bin/python3` (or `.venv/bin/pytest`) — never bare `python3` or `pytest`.** On this machine a bare `python3` resolves to `/Users/darrensy/anaconda3/bin/python3`, which lacks this project's dependencies and fails with `ModuleNotFoundError`. ## Non-negotiables (see plan.md for the reasoning)

### Domain language

- **Brand-neutral vocabulary everywhere.** `venue`, `venue_id`, `venues.json`, `venues_meta.json`, `venue_arrival`. Scope covers Starbucks, Coffee Bean & Tea Leaf, Tim Hortons and potentially independents. Never bake a brand into a contract name, function name, or UI copy. The project is `study-venue-planner` throughout — GitHub repo and local directory alike.
- `venue_type` is **descriptive only** — free-text, not a fixed enum. Originally scoped to six values (`large_cafe`, `mall_cafe`, `office_cafe`, `takeaway_heavy`, `small_kiosk`, `independent_cafe`); opened up during Phase 0 when the real venue list turned up formats those six couldn't describe precisely (a hospital tower, a university campus building, a heritage bungalow, a clubhouse, a tourist food-street unit, a strip-mall unit) — see `decisions.md`, 2026-08-29. Record whatever describes the venue accurately; compute nothing from it until Phase 3 shows it predicts something.

### The decision model

- **Seat confidence is the objective; hours are only a feasibility constraint.** Ranking order: feasibility tier → `seat_confidence` → `backup_strength` → travel burden → `preference` → `surplus_mid`.
- **Dates, not weekdays.** The UI selects `selected_date`; `selected_weekday` is *derived* in `Asia/Singapore`. Hours resolve as: the materialised `current_hours_by_date` entry if the date is inside the current-hours window → **`unknown` if it's a known holiday beyond that window** → regular weekday hours. A holiday past the window must never fall back to regular hours.
- **The current-hours window is computed and validated, never inferred from the data.** `current_hours_valid_from` / `current_hours_valid_through` come from the request's local date — start through start + 6 days, per Google's documented seven-day contract — and every period endpoint date is validated against that window so a change in Google's behaviour fails loudly. Deriving the horizon from the latest date a period *opened* understated it at 4 of 28 venues and is a fixed defect, not a style choice.
- **`current_hours_by_date` is a complete schedule, not a sparse exception list** — every date in the window is materialised as explicitly `known` or `closed`, including dates covered only by a period spanning in from an earlier date. Inside the window a **missing entry is malformed data**, surfaced as such; it must never fall back to regular hours. That fallback was a real defect: a special closure has no opening period, so it produced no entry and the regular schedule was silently resurrected on a day the venue is shut. The field was called `date_overrides`, and the old name is what invited the sparse reading.
- **All time comparisons use absolute minutes**, never raw period offsets. `abs(date, offset) = days_since_epoch(date) * 1440 + offset`, dates in `Asia/Singapore`. Period offsets are relative to *their own* start date, so comparing them directly against an arrival on another date is meaningless — a Tuesday 00:30 arrival must match a Monday `{open: 450, close: 1500}` period, and only absolute minutes make that work. Offsets are for storage; absolute minutes are for arithmetic.
- **Hours resolution is `resolve_hours(venue, target_date)`, a function of an arbitrary date** — never inline logic against the selected date. It applies the current-hours window, the materialised per-date entries, and the holiday rule, returning `{state, periods}`. **Every date goes through it, including the previous date**, because a current-hours entry or an out-of-window holiday on the previous day changes which after-midnight period exists.
- **`venue_close` is derived per arrival, never assumed.** `active_period` is the period containing the arrival. Candidates are `resolve_hours(arrival_date)` **plus `resolve_hours(arrival_date - 1 day)` only when the source-authority rules admit the previous date** (see below) — it is not admitted when the arrival date resolves from a complete materialised current-hours entry, which already carries that span-in coverage. Each is converted to absolute minutes against its own date. Boundary is `period_start_abs <= arrival_abs < period_end_abs`, stated through `period_end_abs` and never a raw `close`, since an `always_open` period has none. **Where several candidates match, take the minimum `period_end_abs`.** Travel may push arrival past midnight; **hours resolve for the arrival date and the date before it, never for the departure date alone.** When travel crosses midnight those coincide — `arrival_date - 1` *is* the departure date — so it does get resolved, as the previous-date candidate rather than the anchor.
  - **The one-day lookback holds by construction, not by luck.** Phase 0 found 3 of 28 venues where Google returns a single period spanning several calendar days (e.g. Sunday 07:30 through the following Saturday close). **Resolved 2026-08-29** (`decisions.md`, "Hours ingestion: five defects"): the fetcher decomposes such a period at ingestion into one entry per calendar day it touches — anchor day keeps its real open time, every other touched day gets `open: 0`, and each carries a `close` equal to the **true remaining distance** to the real close. `resolve_hours` and the one-day lookback are therefore unchanged; each day's entry is self-contained. Trigger is `day_gap = (close.day − open.day) mod 7 >= 2`; entries are **appended**, never overwriting; `day_gap` 0 and 1 are untouched. **Do not cap `close` at 2880** — that was the direction sketched in the earlier Phase 0 entry and it is wrong, losing the true close on spans over two days and reintroducing an artificial midnight close. **`currentOpeningHours` decomposes by calendar-date difference, never `mod 7`.**
- **Open/unknown/closed precedence — positive evidence first.** Build periods from every date whose state is `known` or `closed`, then: (1) a known period containing the arrival returns **open**, *even if the sibling date is `unknown`*; (2) otherwise, if either date is `unknown`, return **unknown**; (3) otherwise return **closed**. Never short-circuit to `unknown` before checking for a match — that discards real information, since a resolvable today settles the question whenever the arrival doesn't fall in yesterday's after-midnight tail. A `closed` date contributes *certainty* (no periods, but definitely not open); an `unknown` date contributes silence, which is not a negative. `unknown` is never silently treated as `closed`.
- **Travel yields two numbers**: `travel_minutes_mid` (band midpoint — display, ordering, Plan B arrival) and `travel_minutes_upper` (band upper edge — the robustness test). Never use the midpoint for feasibility; it pretends a ±2.5 min estimate is exact.
- **Both bounds resolve independently, all the way through.** `arrival_mid` → `active_period_mid` → `effective_close_mid`, and separately `arrival_upper` → `active_period_upper` → `effective_close_upper` — each running its own cross-date authority walk to its own `required_end_abs`. **Never reuse the midpoint's closing time for the upper-bound test** — a later arrival can land in a different period or none at all, which breaks near closing, across midnight, and with split periods. `active_period_upper` being none fails `robust` outright; it is not a zero shortfall.
- **Three feasibility tiers, and every comparison goes through an accessor** — `surplus_*` is a tagged sum type, so no tier test may touch it directly: `robust` (`effective_close_upper` is not `NONE` **and** `passes_feasibility(surplus_upper)`), `tight` (not robust, `effective_close_mid` is not `NONE`, and `passes_feasibility(surplus_mid)` **or** `finite_shortfall(surplus_mid) <= FEASIBILITY_TOLERANCE_MINUTES`, provisional 15 — roughly 4-8% of a 3-6h session), `shorter` (everything else, its own group, including a midpoint `NONE`). Writing `surplus_upper >= 0` or `-surplus_mid <= …` is a type error — the second negates a tag. **`finite_shortfall()` accepts only the finite variant** and rejects `AT_LEAST(0)`; it is never reached with the tag, since `passes_feasibility` short-circuits first. `robust` ranks above `tight`; `tight` carries a thin-margin warning.
- **`baseline_seatability` and `preference` are separate fields and must stay separate.** Baseline (`dependable` / `usually_available` / `mixed` / `poor` / `unknown`) is absolute seat reliability and is the **only cross-venue seat signal before Phase 3**. Preference is study quality only — tables, comfort, Wi-Fi, noise, atmosphere, food. **Preference must never silently carry crowding information**; an earlier design let it do so, which made one number mean two things and hid the signal.
- **`baseline_seatability: unknown` is missing knowledge, not a middle rung.** It never averages, never substitutes for `mixed`, and an `unknown` baseline always yields `unknown` `seat_confidence` regardless of busyness.
- **Never rank on raw busyness, and never claim the band is cross-venue.** Popular Times is normalised to each venue's own peak. The band (`quiet` / `typical` / `busy` / `peak` / `unknown`) answers *"is this an unusually good or bad time for this venue"* — **not** *"is this venue more likely to have a seat than that one"*. Four bands only; `very_quiet` stays deferred — Phase 0 found repeatable deep troughs at several venues (`decisions.md`, 2026-08-29), but adopting the band is a decision left for Phase 1, not something Phase 0's evidence-gathering settles on its own. `peak` takes precedence over `busy`. `N` and `P` are **set from Phase 0's measured curves, never guessed**.
- **Busyness is derived from the historical Popular Times histogram, never live busyness.**
- **`seat_confidence` is an explicit lookup, not a blended score.** `quiet` +1 (capped at `dependable`), `typical` 0, `busy` −1, `peak` −2, `unknown` busyness → baseline unchanged with evidence flagged weaker. **The UI must always show baseline and adjustment separately**, never just the conclusion.
- **Missing busyness must never be treated as `typical`.** It falls back to `baseline_seatability` alone with a visible lower-evidence warning. A source failure must not invent typical conditions. It also must never remove a venue.
- **No numerical seat probability before Phase 3.** Qualitative tiers only until there is real outcome data.
- **The tool must be allowed to return "No low-risk option found for the requested session."** Never promote a `poor` or `unknown` option into a confident-looking Plan A.

### Plan A / Plan B

- **Plan B is recalculated from Plan A, never taken from the origin-ranked list, and carries both bounds.** The first leg's uncertainty compounds into the second, so a single collapsed arrival is wrong:

  ```
  plan_b_departure_mid   = plan_a_arrival_mid   + SEAT_CHECK_BUFFER_MINUTES
  plan_b_departure_upper = plan_a_arrival_upper + SEAT_CHECK_BUFFER_MINUTES
  plan_b_arrival_mid     = plan_b_departure_mid   + fallback_travel_minutes_mid
  plan_b_arrival_upper   = plan_b_departure_upper + fallback_travel_minutes_upper
  ```

  `fallback_travel_minutes_*` derive from `fallbacks[].travel_band` exactly as `access` bands do. `SEAT_CHECK_BUFFER_MINUTES` (provisional 10) applies to both bounds. Plan B then resolves `active_period_mid` and `active_period_upper` **independently**, each on its own arrival date, and gets its own `robust`/`tight`/`shorter` tier by the same rule as Plan A. Never reuse Plan A's periods or collapse Plan B to one arrival.
- **Plan B is not a simplified calculation.** It uses the identical machinery as Plan A — absolute-minute active-period lookup, both travel bounds resolved independently, its own feasibility tier — at the delayed arrival, with `fallbacks[].travel_band` supplying its travel numbers. Anything less recommends the rescue on weaker evidence than the thing it rescues.
- **`backup_strength` is `strong` / `salvage` / `none`, graded by whether the *requested session* survives** — not merely by whether somewhere is open. `strong` = the requested session fits (`robust` or `tight`) at the fallback with confidence ≥ `PLAN_B_MIN_CONFIDENCE`. `salvage` = at least `PLAN_B_MIN_SESSION_MINUTES` (provisional 90) remains and confidence ≥ `PLAN_B_MIN_CONFIDENCE` (`mixed`), **but the requested session does not fit**. `none` = below either floor, or no valid fallback. Derived from fallbacks viable at delayed arrival, never from proximity alone.
- **A `salvage` option must be labelled `salvage` and must state its actual duration** — "gives 1h40m, not the 6h you asked for". Never present it as satisfying the request. `salvage` replaces the earlier `weak`, which conflated "a bit further away" with "half the session you wanted".
- **Never multiply venue probabilities** to claim a combined chance of a seat somewhere. Neighbouring venues' crowding is correlated.
- **No full venue-to-venue travel matrix.** Hand-picked `fallbacks` links between plausible neighbours only.

### Data and infrastructure

- **No deployed backend, no server-side code, no API keys shipped in `web/`.** Static files only, GitHub Pages from this public repo, serving from the repo root. Fetcher credentials in a gitignored `.env`. "No server" does not forbid a local one — under the inlined-data design none is needed.
- **No live data of any kind** — no real-time busyness, no weather API, no transit API. Rain is a manual toggle.
- **`build/refresh.py` is the sole owner of `data/venues.json` and `web/index.html`, and its step order is load-bearing.** **Coarsen new raw visits FIRST**, against the currently deployed histogram — running it after the fetch stamps every new visit with the *new* busyness value and silently destroys the lineage Phase 3 depends on. Then fetch, validate, merge with last-known-good, record per-source `last_attempt_at` / `last_success_at` / `status`, replace atomically, regenerate. Fetchers return data; they never write files. There is deliberately **no global `generated_at`**. `ok` = fetched this run; `stale` = failed, showing last-known-good; `failed` = failed with no last-known-good.
- **`data/venues_meta.json` and `data/holidays.json` are hand-maintained and must never be written by a script.** `brand`, `venue_type`, `area` and `baseline_seatability` live in meta, not in the generated file, precisely so a refresh cannot clobber them — `area` included, since the Places API returns no clean neighbourhood field and it is a judgement call. They are merged onto the venue object at generation time.
- **`web/index.html` is generated and fully self-contained.** From `web/index.template.html`, inlining the data (`<script type="application/json">`), the **code** and the **styles**. Never hand-edit it. The source files stay real files — `tests/js/` imports `ranking.js` directly. The page loads **no external assets except an optional web app manifest, and functions completely without it** — no `fetch()`, no `localStorage`, no unresolved imports. Use that wording; "no external assets" alone is false, since the manifest is one.
- **The module inlining contract is specific.** `ranking.js` is a real ES module with `export` declarations (Node's test runner is its only importer). `app.js` imports from it via one fixed-form `import { … } from "./ranking.js";` at the top. The generator emits **one** `<script type="module">` containing `ranking.js` in full, then `app.js` **with that import line removed** — shared module scope makes the bindings visible without it. Leaving the import in would make the browser fetch `./ranking.js`, defeating the entire design. **Consequence: the two files share one top-level scope after concatenation, so their top-level names must not collide** — that is a real constraint on how the code is written, and it needs a test.
- **Unicode-escape `<` in embedded JSON** — `json.dumps(data).replace("<", "\\u003c")`. This is a JSON-level escape, not an HTML one: HTML entities are *not* decoded inside `<script>`, so `&lt;` would corrupt the value instead of protecting it. A `notes` field or venue name containing `</script>` would otherwise terminate the block. Needs a test using a value that actually contains `</script>`, asserting both that the page parses and that the value round-trips.
- **The manifest is the sole external asset and it is optional** — Safari's `data:` URI manifest support is unreliable, so it stays a separate file. "Optional" precisely: when it is absent or fails to load (exactly what happens to the AirDropped copy on `file://`), nothing degrades except home-screen install. All data, logic and features work.
- **All paths are relative** (`./index.html`, `./`), never absolute. For a project Pages site the repo name is a path prefix, so `/web/index.html` 404s — and relative paths keep the `file://` copy working.
- **Two independent fetch interfaces** — `fetch_hours(place_id)`, `fetch_busyness(place_id)`. They fail independently. Never take opening hours from the busyness scrape or a third-party aggregator.
- **Google Places API is the primary hours source**, chosen because it gives one consistent identity/hours/`businessStatus` interface across every brand. Brand-specific locators would mean a separate fragile integration per chain and no closure signal; the Starbucks SG locator is now only a timeboxed cross-check, never an architectural input.
- **Hours use explicit `known` / `closed` / `unknown` states.** A fetch failure must never be representable as a closure. Integer minutes from local midnight; `close > 1440` means after-midnight, and **`close` can legitimately reach `7 * 1440`** on a decomposed multi-day entry — a large value is not evidence of a parse bug.
- **A 24-hour venue has no `close` at all** — `{"open": 0, "always_open": true}`. The period **records no known close**; that is a fact about the source period, not a promise about other dates. Once the walk covers the required span without reaching a close, `effective_close` is **`COVERED`** — never a claim that the venue does not close. `closing_buffer` has nothing to apply against within the verified span, `surplus_*` is **`AT_LEAST(0)`** rather than a figure, and `latest_leave_at` is `UNDETERMINED`, meaning **"no known closing constraint within the verified span"** — never "there is no latest departure". Nothing searches past `required_end_abs`, so nothing may claim what lies beyond it, and an unverified later close must never be used for exact surplus or later-departure advice. `UNBOUNDED` stays a **period-level** value used only for containment and never travels into a feasibility claim.
- **`AT_LEAST(0)` is a tagged outcome, not a number.** `surplus_*` is a sum type — a real integer margin, or the tag. Never compare, subtract from, or format the tag as an ordinary number. Exactly three accessors may consume it: `passes_feasibility()` → **true** (so a `COVERED` upper bound can be `robust`); `sort_key()` → **0**, the proven lower bound, so it never out-ranks a genuinely-verified surplus on a tiebreak it did not earn; `display()` → **no numeric margin** ("fits — margin not established"). **`display()` must never fall back to `sort_key()`** — rendering the tag as "0" would claim the venue closes exactly at your deadline when its closing time was never established. The two failure modes are opposite, which is why sorting and display are separate accessors.
- **`NONE` and `UNKNOWN` are different outcomes.** `NONE` (no active period at that arrival) is a definite "not open then" and **never unranks a venue on its own**: an upper-bound `NONE` fails `robust` while the midpoint is still evaluated and may be `tight`; a midpoint `NONE` falls to `shorter`. Only `UNKNOWN` — unresolved hours — removes a venue from ranking. `effective_close` is **never called with a missing active period**; the caller returns `NONE` instead. The old `{"open": 0, "close": 1440}` fabricated a midnight close and relegated genuinely 24-hour venues to `shorter` every evening. **The unbounded result is a property of the resolved period, never of the venue** — a current-hours closure or an `unknown` date still overrides the regular 24/7 schedule. `null` is never used for a close; it was already rejected for making a fetch failure indistinguishable from a closure.
- **`truncated` endpoints are window edges, never events.** Google clips periods at the seven-day window boundary and flags the clipped end. `open.truncated` is valid only at the window's first date, 00:00; `close.truncated` only at the final date's boundary. A truncated close reported as 23:59 normalises to the **exclusive next midnight** and carries `continues_beyond_window: true`, which propagates to **every** entry of a decomposed truncated chain. Interior or inconsistent truncation **fails validation** rather than being guessed through. This affects 7 of 28 venues, one of which has no unusual hours at all — truncation is a property of the window, not of the venue.
- **Feasibility runs off the effective continuous known open run, not the raw active period.** Derive the run from the active period, resolved for the midpoint and upper bounds **independently**; where a period ends at a `continues_beyond_window` boundary, resolve the next date and **join only if its known period begins exactly at 00:00**. A gap at 00:00 means the venue genuinely closes there — that is a *known* close. Bounded to at most two calendar dates, since `duration + closing_buffer` is under 24 hours; no lookahead loop, no cycle bound. `closing_buffer` sits inside the span because it can cross midnight when the session does not.
- **A known shortfall and an unknown boundary are different outcomes, and the tiers must not conflate them.** Compute `surplus_*` against the run's `effective_close` and apply the ordinary tiers: `COVERED` or sufficient finite coverage **at the upper bound** is `robust` (full coverage at the midpoint alone is not), a **known** shortfall within `FEASIBILITY_TOLERANCE_MINUTES` is still `tight` with its thin-margin warning, a larger known shortfall is `shorter`. **Only an `unknown` boundary makes a venue hours-unknown and unranked** — a small measured shortfall never does. Demanding literal continuous coverage of the whole interval would silently abolish the `tight` band.
- **`UNBOUNDED` is a runtime value, never serialised.** JSON has no `Infinity` literal, so an always-open period is stored as the **absence of a `close` key** plus `always_open: true`, and `ranking.js` derives the unbounded end via `period_end_abs(d, p)` when building candidate periods. Reading `p.close` directly is a bug — it yields `undefined` on precisely the venues that are open longest.
- **The cross-date walk is sequential and lazy, and stops at the first known close.** Order: start at the active period; a known close before the next date boundary returns immediately; `required_end_abs` covered returns `COVERED`; the following date is resolved **only** when the run actually reaches that boundary *and* `required_end_abs` lies beyond it. **A date the run never reaches is never resolved and can never contribute `UNKNOWN`** — arrival Mon 18:00 with a known Mon 22:00 close and an unknown Tuesday is a *known shortfall* (`tight`/`shorter`), never hours-unknown. Resolving every intersected date up front, as an earlier draft did, unranks venues whose closing time is perfectly well known.
- **A period's own extent is never evidence about a date it crosses and actually reaches** — **whatever the shape**: ordinary overnight, multi-day, truncated or `always_open` alike. A finite Mon 22:00–Tue 02:00 regular period must not establish known Tuesday coverage when Tuesday is an out-of-window known holiday, and neither must a finite multi-day suffix entry. Scoping the walk to `always_open` and `continues_beyond_window` only leaves both finite cases broken.
- **`always_open` specifically means "no known close *in this source period*", never "open forever".** A 24/7 *regular* schedule says nothing about a date the current-hours window explicitly closes, nor about a known holiday beyond that window — so a session running past midnight into an out-of-window holiday **that the run actually reaches** is **hours-unknown**, not `robust` inherited from the prior period. An `always_open` period yields `COVERED`, never a no-close claim, and only once every date the run reaches has agreed.
- **`effective_close(venue, active_period, arrival_abs, required_end_abs)` takes what it needs explicitly** — `venue` so it can call `resolve_hours()` and read source authority for any date, `required_end_abs` so it knows how far coverage must be proven. It must not depend on unstated surrounding variables.
- **The formulas consume `effective_close_mid` / `effective_close_upper`, never a raw `active_period.period_end_abs`.** Each bound derives its own run independently. **`effective_close` returns exactly one of: a finite absolute close, `COVERED`, or `UNKNOWN`** — never `UNBOUNDED`, which is period-level containment only and is never a feasibility result. **`NONE` is returned by the caller** when `active_period` is missing; `effective_close` is not called at all in that case. **Branch on the outcome before any arithmetic** — subtracting from a value that may hold `COVERED`, `NONE` or `UNKNOWN` is a type error: `UNKNOWN` → hours-unknown with no tier and no metrics; `NONE` → metrics undefined (upper fails `robust`, midpoint falls to `shorter`); `COVERED` → `usable_minutes = duration`, `surplus = AT_LEAST(0)`, `latest_leave_at = UNDETERMINED`; a finite close → the numeric formulas.
- **The `required_end_abs` boundary is inclusive on the close side.** A finite close **at exactly** `required_end_abs` is returned as a finite close, giving an exact `surplus` of **0** — a verified thin margin. Only a close **strictly beyond** `required_end_abs` yields `COVERED`, because that is the case the walk did not reach.
- **`robust` is judged on the upper bound alone.** Full coverage at the midpoint does not make a venue `robust` — that is the point of resolving both bounds independently. A venue that fits on an optimistic journey but not a pessimistic one is `tight`.
- **Source authority decides which dates may contribute periods, not just which entry wins.** Current hours outrank regular hours. If the arrival date is **inside the current-hours window**, its materialised entry is complete and authoritative — it already contains span-in coverage — and **the previous date is not admitted**; otherwise a 24/7 *regular* schedule would match an arrival on a date the current hours record as **closed**, and positive-evidence precedence would return `open` on a day the venue is shut. If the arrival date is a **known holiday outside the window**, return `unknown` immediately: a regular overnight period carried in from the previous day must never overturn the holiday rule. **This does not weaken positive evidence**, which covers a *known* arrival date with an `unknown` sibling — these cases are the reverse.
- **`data/venues_meta.json` carries no exact travel minutes and no real origin names.** Ordinal rank plus a coarse band, under `origin_a` / `origin_b`. `travel_minutes` is the **band midpoint** (±2.5 min) — the same derivation applies to `fallbacks[].travel_band`. This repo is public and exact minutes to published coordinates would trilaterate home and work.
- **Seat log outcomes stay `seat` | `no_seat`.** The committed `data/seatlog.csv` is coarsened to `(venue_id, day_of_week, hour, outcome, histogram_busyness, histogram_fetched_at)` — the calendar date is dropped for privacy, but the busyness value **in effect at visit time** is captured (which requires the coarsen-before-fetch order above). The file is append-only and chronological, so **relative visit ordering survives** — "last visit" is answerable. Absolute dates, intervals and seasonality are what's genuinely lost. The raw dated file's canonical home is iCloud Drive, append-only, never rewritten from code. **Local staging is restricted to two gitignored paths — `data/raw/` or `data/seatlog.raw.csv` — and no others.** The ignore rules are deliberately narrow so `data/seatlog.csv` (the coarsened committed output) stays committable, which means a raw file staged anywhere else would **not** be ignored and would publish a timestamped movement history to a public repo. Any new staging path needs its ignore rule added in the same commit.
- **Holiday handling is per venue**, via `holiday_policy` in meta: `unknown` (default) or `substitute_sun`. A global Sunday substitution is plausible for mall cafés and wrong for kiosks, office cafés and independents — `unknown` is the honest default and substitution an explicit per-venue claim.
- **The rain toggle's effect is explicit**, via `wet_weather_mode` in meta naming which mode replaces which per origin. A mode with no substitute is simply unavailable in the rain. The resulting later arrival can shift the busyness band and the feasibility tier — show that, never reorder silently.
- **`make refresh` never commits.** Inspecting the diff, committing and pushing stay separate manual actions.
- **Vanilla HTML/CSS/JS in `web/`** — no framework, no npm, no bundler. The data-inlining step is not a build system in this sense. Pure logic goes in `ranking.js` with no DOM imports.

## Testing

Small and deterministic. No mocking frameworks, no live-network tests.
